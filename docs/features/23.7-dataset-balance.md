# Balanced dataset + provenance

> Phase 7 of [exec-plan 23 — Observability + Evals SOTA](../exec-plans/23-observability-evals-sota.md).

## What it does

Equalizes per-category counts in each suite and records every case's origin
(`real` vs `synthetic`), making class balance and provenance auditable.

## Suite matrix (category × suite × source)

| Category | regression | capability | total |
|---|---|---|---|
| status | 5 | 6 | 11 |
| refunds | 5 | 4 | 9 |
| availability | 5 | 4 | 9 |
| shipments | 5 | 4 | 9 |
| prices | 5 | 4 | 9 |
| **total** | **25** | **22** | **47** |

> `regression` is strictly balanced 5×5 (it's the gate). `capability` keeps a **minimum
> of 4 per category** but carries 2 extra `status` cases (`status-003`/`status-004`)
> recurated out of the regression gate for being ambiguous — the trend suite is the right
> home for them. See [23.3](23.3-capability-vs-regression.md).

**Source:** all 45 cases are `synthetic` (hand-authored). There are **0 `real`** cases —
the product has no production email corpus yet (MVP not shipped with real data per
`AGENTS.md`). The `real`/`synthetic` distinction is in place so real cases can be added
and tracked the moment production data exists.

Five synthetic cases were added in this phase to balance `capability` from 4/3/3/3/2 to
4/4/4/4/4 (ids prefixed `synth-`, each with a `provenance_note`).

## How it works

- `EvalCase.source: Literal["real","synthetic"]` is **required** — a dataset row missing
  it is rejected at load (`ValidationError`). Optional `provenance_note` documents origin.
- `CaseMeta` (framework metadata) also carries `source`.
- The console report prints a `Source  real N · synthetic N` line.
- `--filter source=synthetic|real` works like any other field filter.

## Files involved

| File | Role |

## Design decisions

| Decision | Discarded alternative | Reason |
|---|---|---|
| `source` required (no default) | optional with default | forces every row to declare provenance; load-time rejection |
| Label all current cases `synthetic` | claim some are `real` | honest — there is no production corpus yet; don't fabricate provenance |
| Balance `capability` to 4×5 | leave imbalanced | macro-F1 and per-category trends are only fair on balanced support |
| Keep synthetic additions in `capability` | add to `regression` | regression stays the locked core; synthetic noise belongs in the trend suite |

## Gotchas / Edge cases

- Adding `source` is a breaking dataset-schema change: any external JSONL must include it.
- Synthetic cases can carry distributional bias — they live in `capability` (trend), not
  the `regression` gate, so they don't pollute the must-pass set.

## Follow-ups

- When real customer emails are available, add them with `source="real"` (anonymized) and
  re-run the balance check; consider a `--by-source` accuracy breakdown then.
