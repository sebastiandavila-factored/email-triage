# Prompt versioning (Logfire Prompt Management)

> Phase 1 of [exec-plan 23 — Observability + Evals SOTA](../exec-plans/23-observability-evals-sota.md).

## What it does

Moves the triage system prompt out of code and into a **Logfire-managed variable**, so
it can be versioned and promoted from the Logfire UI without a deploy. A code fallback
(`SYSTEM_PROMPT`) guarantees the `/triage` critical path keeps working even if Logfire
has no managed prompt yet or is unreachable.

## How it works

The variable is registered **once at import time** in `email_triage/deps.py`:

```python
_SYSTEM_PROMPT_VAR = logfire.var(name="prompt__email_triage_system", default=SYSTEM_PROMPT)
```

`logfire.var(name=...)` is a *registration* call — calling it twice with the same name
raises `ValueError("already been registered")`, so it must live at module scope, not
inside a function.

Resolution happens **once per process** (not per request):

```python
@lru_cache(maxsize=1)
def get_system_prompt() -> str:
    settings = get_settings()
    return _SYSTEM_PROMPT_VAR.get(label=settings.prompt_label).value
```

- `.get(label=...)` reads a locally-cached snapshot of the managed variable; when no
  version is published it returns the `default=` with `ResolvedVariable.reason ==
  "code_default"`.
- `@lru_cache` + an eager warm-up in the lifespan means a single resolution at startup;
  `get_llm_service()` builds the `LLMService(system_prompt=...)` from that value and the
  agent is constructed once.

The `lifespan` in `main.py` warms the cache and runs the governance guard before any
request is served:

```python
prompt = get_system_prompt()
assert_category_coverage(prompt)
llm = get_llm_service()
```

### Governance: prompt ↔ `Category`

The 5 categories are frozen in `schemas.Category` and code review is the gate for
changing them. A prompt edited in the Logfire UI bypasses that gate, so on startup
`assert_category_coverage()` checks the resolved prompt still mentions every category
and logs a structured `prompt.category_drift` **warning** on drift. It never raises —
the in-code fallback is always valid, so a loud warning beats crashing the service.

**Source of truth:** the in-code `SYSTEM_PROMPT` (in `services/llm.py`) is canonical.
Any Logfire UI edit must keep the 5 categories; the drift guard surfaces violations.

## Files involved

| File | Role |
|---|---|
| `email_triage/services/llm.py` | `LLMService.__init__(..., system_prompt=SYSTEM_PROMPT)`; agent built with it. `SYSTEM_PROMPT` const kept as fallback. |
| `email_triage/deps.py` | `_SYSTEM_PROMPT_VAR` registration, `get_system_prompt()`, `assert_category_coverage()`, `get_llm_service()` wiring. |
| `email_triage/config.py` | `prompt_label: str = "production"`. |
| `email_triage/main.py` | lifespan warm-up + drift guard. |
| `tests/test_prompt_versioning.py` | unit tests (fallback, resolve-once, label, drift guard, prompt reaches agent). |

## Design decisions

| Decision | Discarded alternative | Reason |
|---|---|---|
| Register `logfire.var` at module scope | Register inside `get_system_prompt` | Registration is not idempotent — repeated calls raise `ValueError`. |
| Resolve once via `@lru_cache` + lifespan warm-up | `.get()` per request | No per-request lookup on the critical path. |
| In-code `SYSTEM_PROMPT` is source of truth | Logfire UI is source of truth | Critical path must survive a Logfire outage; code review stays the gate for categories. |
| Drift guard warns, never raises | Raise on drift | Fallback is always valid; crashing would be worse than a loud warning. |

## Gotchas / Edge cases

- `logfire.var(name=...)` can only be registered once per process — never call it from a
  function body.
- Tests patch `deps._SYSTEM_PROMPT_VAR.get` (the resolution seam), not `logfire.var`.
- `get_system_prompt.cache_clear()` is called in tests to avoid cross-test cache
  pollution; the lifespan re-resolves on next startup.
