Part 1

OTEL observability
with Logfire

Start with the familiar to set the OTEL vocabulary, which we reuse in evals.

What is OpenTelemetry?

An open, vendor-neutral standard (CNCF) for producing telemetry: traces, metrics and logs.

Decouples instrumenting from storing

Instrument once with the API/SDK; export to any backend (Logfire, Jaeger, Grafana, Datadog…).

Semantic conventions

Standard attribute names (http.method, gen_ai.*) → different tools understand the same thing.

your code → OTEL SDK → [optional Collector] → backend (Logfire)

The key idea: you're not married to a vendor. Swap the backend and your instrumentation stays the same.

Conceptual anchor. OTEL is to observability what SQL is to databases: a standard. The point for the team: we instrument against OTEL, not against Logfire. Logfire is swappable. Semantic conventions matter: gen_ai.* is the convention for LLMs, which is why online-eval events (gen_ai.evaluation.result) are standard.

Anatomy of a span

The span is the building block. One span = one unit of work with a name and a duration.

  • name + start/end (→ duration) + status (ok/error).
  • attributes: key–value pairs (low cardinality).
  • trace_id = the whole request · span_id = this step · parent → tree.
  • context propagation: the trace_id travels across functions/services → distributed trace.
with logfire.span("triage.sync") as span:
    span.set_attribute("endpoint", "sync")
    span.set_attribute("email.body_chars", n)
    result = await llm.triage(req)   # child span
    span.set_attribute(
        "triage.result.category", cat)

The handler opens a span; the LLM run and the httpx call hang off it as children → a tree that tells the request's story.

This grounds the vocabulary we use all talk. The span tree is literally what we see in Logfire and what span-based evaluators read later (ctx.span_tree). trace_id/span_id also go into every structlog line to correlate logs ↔ traces.

What is Logfire?

Pydantic's observability backend — OTEL-native, not proprietary.

Ergonomic SDK over OTEL

logfire.span(), metric_*() and one-line auto-instrumentation. Under the hood it's plain OTEL.

Pydantic-aware

Understands Pydantic AI, validations and models — rich instrumentation with no effort.

Queryable with SQL

Traces are queried with SQL (Postgres behind it): dashboards and alerts over your attributes.

Production-ready

Scrubbing (PII), sampling (head/tail) and, new: prompt management + evals.

Because it's OTEL, tomorrow you can send the same signal to another backend without touching code.

Logfire = thin SDK + backend. The differentiator vs others: it's born from Pydantic, so it understands Pydantic AI natively, and everything is queryable with SQL. Most important for avoiding lock-in: underneath it's standard OTEL. And the two features we use in parts 3 and 4 (prompt management + evals) live right here.

Three signals, one protocol

Traces / spans

The tree of what happened in a request: handler → LLM → httpx.

Metrics

Aggregated counters and histograms: latency, errors, confidence.

Logs

Structured events with request_id (structlog in JSON).

Logfire is an OpenTelemetry backend: instrument once and the same signal serves debugging, dashboards and evals.

Key idea: OTEL is an open standard, Logfire is just the backend. And crucially for today: the same span signal we use to observe production is what span-based evaluators read later.

Our configuration

logfire.configure(
    send_to_logfire="if-token-present",
    environment=_settings.logfire_environment,
    sampling=SamplingOptions(head=_settings.logfire_sample_rate, ...),  # tail sampling
    scrubbing=ScrubbingOptions(...),                                    # PII out
)

# Auto-instrumentation: one line per layer
logfire.instrument_pydantic_ai()     # spans for each agent run + tokens
logfire.instrument_pydantic()        # model validations
logfire.instrument_system_metrics()  # CPU / RAM
logfire.instrument_httpx()           # outbound calls (Groq)
logfire.instrument_fastapi(app)      # HTTP spans per endpoint

email_triage/main.py — declarative instrumentation, without polluting business logic.

Show that with a few lines we get tracing of FastAPI, Pydantic AI, httpx and system metrics. Tail sampling: we decide which traces to keep at the end of the trace (once we know if there was an error / high latency), not at the start. Scrubbing strips sensitive data.

Part 2

Evals fundamentals

Based on “Demystifying evals for AI agents” — Anthropic, 2026.

Switch to evals theory. It's the conceptual frame we then implement with Pydantic Evals.

What is an eval?

A test for an AI system: input → grading logic → measure of success.

The useful analogy (Pydantic): Case + Evaluator = a unit test · Dataset = the suite · Experiment = running pytest and getting a report.

The difference from unit tests: AI systems are probabilistic. The score is usually qualitative/graded, not binary pass/fail.

Simple definition. The testing analogy lowers the team's anxiety: they already write tests. The difference is non-determinism, which forces graded scores and running multiple times.

This glossary means that when we discuss, we all say the same thing. The point: each term already has a counterpart in our code. We're not starting from zero.

Three families of graders

Code-based

exact match, regex, static analysis, state checks.

✅ fast, cheap, reproducible
❌ brittle to valid variations

Model-based (LLM judge)

rubrics, pairwise comparison.

✅ flexible, captures nuance
❌ non-deterministic, needs calibration

Human

SME review, A/B, inter-annotator.

✅ gold standard
❌ expensive and slow

Anthropic's rule: deterministic whenever you can, LLM where needed, humans to calibrate.

The project already has the first two: code-based (category equality + metrics) and model-based (the JudgeAgent). What's missing is the human layer, even a spot-check, to calibrate the judge. Golden rule: don't use an LLM judge if a deterministic check is enough.

Capability vs Regression

capability

“What can it do well?”
Starts at a low pass rate. It's the hill to climb. Measures progress.

regression

“Does it still do what it did?”
Pass rate ~100%. Guards against backsliding. A drop = something broke.

Shipped: regression 25 cases (5×category, strict gate 0.95) · capability 22 cases (edge/english/tone, trend 0.70). make eval-regression with --check exits ≠0 if it drops below the threshold.
Real finding: status-003/004 were stably predicted as shipments (defensible ambiguity). Instead of lowering the threshold, we re-curated them → moved to capability, and added 2 clear status cases to regression. A gate you loosen so it passes is not a gate.
Anthropic's key distinction, already implemented. The mixed dataset.jsonl was split into two disjoint suites. The ambiguous-status finding is the perfect example of Anthropic's step 7 (read transcripts): the harness wasn't broken and the model wasn't wrong — they were borderline labels in the wrong suite. Moved to capability, and regression is at 100%.

Non-determinism: pass@k vs pass^k

pass@k

Probability of at least 1 success in k tries.
Rises with k. “One success is enough.”

pass^k

Probability that all k pass.
Falls with k. For customer-facing agents.

75% per trial, 3 trials → pass^3 = 0.75³ ≈ 42%. Our temperature=0.2 is not 0: the same email can classify differently. For support, pass^k is the honest metric.
Shipped: --repeat K (via the framework's repeat=) + compute_pass_hat_k() from case_groups(), with a flaky list (correct on some-but-not-all runs). make eval-passk K=5.
Already implemented. Since we reply to real customers, what matters is "always right", not "right sometimes". pass^k counts only cases correct across all k runs; a run that errored counts against it. Tested invariant: pass^k ≤ accuracy. We also hardened the gate: if >20% of cases error (rate limit), accuracy is computed only over survivors and could pass vacuously — now the gate detects it and fails.

Anthropic's roadmap, in 8 steps

  1. Start early — 20–50 tasks from real failures is enough.
  2. Start from what you already test by hand (bugs, support).
  3. Unambiguous tasks + reference solution.
  4. Balanced sets (test when it SHOULD and when it SHOULDN'T).
  5. Robust harness + isolated environment per trial.
  6. Thoughtful graders; partial credit; LLM judge with an “Unknown” exit.
  7. Read the transcripts — don't trust the number alone.
  8. Watch for saturation; keep the suite alive.

An eval at 100% no longer signals improvement — it only works as a regression test.

You don't need hundreds of cases to start. Step 6 — read transcripts — is the most ignored and the most important: a score that won't climb may be a broken grader, not a bad model. We connect this later to the Logfire view.

No single layer catches everything

The “Swiss cheese” model: combine methods, what slips past one is caught by another.

Automated evals CI/CD, pre-launch
Production monitoring ground truth
A/B testing big changes
User feedback thumbs-down
Transcript review intuition
Human studies calibrate judges

Evals are one layer. Our observability is already another (production monitoring).

Reassuring message: evals don't replace monitoring or user feedback. They complement each other. We already have production monitoring (part 1). Evals add the fast, reproducible pre-deploy layer.
Part 3

Prompt versioning
with Logfire

Getting the prompt out of the code without a redeploy.

First core ask. Today the prompt is hardcoded; we're going to version it.

The problem

SYSTEM_PROMPT = """You are an email triage system..."""   # in services/llm.py
  • Every prompt tweak = commit + redeploy.
  • No history of “which prompt was in prod on Tuesday”.
  • Rollback = revert code and redeploy.
  • Product/support can't touch the prompt without touching the repo.
Frame the pain before the solution. The prompt is the parameter we iterate on most in an agent, and it's exactly the one most coupled to deploys.

Two concepts: prompt and version

Prompt

The unit you author. It has a name (Email Triage System), a slug (email-triage-system), template text and settings.

Version

Immutable snapshot of the template (v1, v2, v3…) with author and timestamp. Freezes only the text, not the settings.

And a third: the label (e.g. production) — a movable pointer to a version. The app consumes by label, not by number.
Mental model: like git tags + a "production" pointer. Versions are immutable; the production label moves. Important: the version freezes only the template text.

Save ≠ Promote

1
Save

Save a version on the Prompts page. Iterate on drafts freely.

2
Promote

Move the production label on Managed Variables. Only now does what prod imports change.

Splitting the two steps = iterate risk-free + explicit, auditable promotion.

This decoupling is the governance key: saving many versions doesn't affect production until you consciously move the label. And rollback is just moving the label back.

The code in the app (what we shipped)

import logfire
from functools import lru_cache

# ⚠️ logfire.var() REGISTERS the variable and is NOT idempotent → module level, once.
_VAR = logfire.var(name='prompt__email_triage_system', default=SYSTEM_PROMPT)

@lru_cache(maxsize=1)                 # resolved 1×/process, NEVER per request
def get_system_prompt() -> str:
    return _VAR.get(label=settings.prompt_label).value
    # if Logfire doesn't respond → ResolvedVariable.reason == 'code_default'
    # → uses the code default: the critical path doesn't break.

# Governance prompt ↔ Category (guard in the lifespan, warns, doesn't crash)
def assert_category_coverage(prompt: str) -> None:
    missing = [c.value for c in Category if c.value not in prompt]
    if missing:
        _log.warning("prompt.category_drift", missing_categories=missing)

Two production surprises: logfire.var() registers once (call it 2× and it blows up), and .get() returns a ResolvedVariable with .value — it's not a context manager.

The REAL pattern that ended up in the repo. I found live that logfire.var() isn't idempotent: calling it inside a function broke the test-suite with "already registered". So it lives at module level and only .get() is called per resolution, cached with lru_cache (resolved once in the lifespan, zero fetch per request). The default guarantees the fallback. And the category guard protects governance: if someone edits the prompt in the UI and drops a category, it warns via log without taking down the service.

Applied to email-triage ✅ delivered

  1. ✅ get_system_prompt() resolves by label, injected via Depends() (the repo's DI pattern).
  2. ✅ Resolved once in the lifespan (@lru_cache), no per-request fetch — the critical path (1–3 s) pays no lookup.
  3. ✅ default=SYSTEM_PROMPT: the source of truth stays in code; Logfire only overrides it if a version is published.
  4. ✅ Governance guard prompt ↔ Category (warns if the UI drops a category).
Manual step (UI): creating the prompt and moving the production label is a human action. The code works with the fallback until that exists. Live rollback: move the label to v(n-1) — no commit, no deploy.
Delivered respecting the repo's patterns (DI, lifespan). The source of truth for categories is still the code (default + Category enum + guard); Logfire gives agility to iterate the text. Creating/promoting in the UI is the only manual step, and the code doesn't depend on it to boot.
Part 4

Evals with
Pydantic Evals

From the home-grown harness to the framework — without losing what we have.

Second core ask. We connect part 2's theory to the concrete API.

The data model

Dataset (1) ───────── (Many) Case
   │                      │
   └── (Many) Experiment ─┴── (Many) Case results
         └── (1) Task
         └── (Many) Evaluator

Code-first: everything is defined in Python (or serialized YAML/JSON). With Logfire, results show up in the web UI for comparison and collaboration.

Code-first philosophy: unlike fully web-based platforms, here evals live in the repo, versioned with git, and Logfire is the visualization layer. This fits how we already work.

A minimal eval, end-to-end

from pydantic_evals import Case, Dataset
from pydantic_evals.evaluators import Evaluator, EvaluatorContext, IsInstance

case = Case(
    name='refund_en_01',
    inputs={'subject': 'Can I return my order?', 'body': '...'},
    expected_output='refunds',
    metadata={'difficulty': 'easy', 'lang': 'en'},
)

class CategoryMatch(Evaluator[dict, str]):          # your is_correct, as an evaluator
    def evaluate(self, ctx: EvaluatorContext[dict, str]) -> float:
        return 1.0 if ctx.output == ctx.expected_output else 0.0

dataset = Dataset(
    name='email-triage',
    cases=[case],
    evaluators=[IsInstance(type_name='str'), CategoryMatch()],
)

async def task(inputs: dict) -> str:
    resp = await llm.triage(TriageRequest(**inputs))
    return resp.category.value

report = dataset.evaluate_sync(task)                # = run the suite
report.print(include_input=True, include_output=True)

Real repo detail: expected_output is typed as the task's output (TriageResponse), so we store the expected category in metadata (CaseMeta) and the evaluator reads it from there.

Here you see how much of what we had maps directly: each jsonl line is a Case, is_correct is an Evaluator, run() is evaluate_sync. The migration was mechanical. The one non-obvious tweak: since expected_output must match the output type, the ground-truth category lives in metadata, not in expected_output. We reused metrics.py untouched, rebuilding EvalResult from report.cases.

LLM judge: home-grown vs built-in

Today: evals/judge.py
JudgeAgent with a 5-dimension rubric (relevance, language_match, tone, correctness, overall), temperature=0.1.

from pydantic_evals.evaluators import LLMJudge

dataset.add_evaluator(LLMJudge(
  rubric=(
    "The reply is polite, in the same "
    "language, and invents no order details."
  ),
))
Shipped: the JudgeAgent is reused inside a custom Evaluator (JudgeQuality); we added verdict="unknown" so it can abstain instead of inventing (excluded from means + unknown_rate), and --judge-sample N exports to evals/calibration/*.jsonl for human spot-check.
We didn't throw away the JudgeAgent: we wrapped it in a framework Evaluator (numeric scores → report scores; language_match → assertion; verdict → label). Anthropic's "Unknown" advice we implemented as a Literal verdict: when it abstains, scores go None and are excluded from means, but it's counted in unknown_rate. The export leaves the seam for human calibration (human_verdict null for a person to fill in).

Span-based: evaluate the how

import logfire
from pydantic_evals.evaluators import HasMatchingSpan

logfire.configure(send_to_logfire='if-token-present')

dataset.add_evaluator(
    HasMatchingSpan(
        query={'name_contains': 'triage'},
        evaluation_name='called_the_llm',
    )
)
# in custom evaluators you have the full tree: ctx.span_tree
The eval reads the same OTEL span tree you see in prod → your eval assertions stay aligned with your telemetry. This closes the loop Part 1 ↔ Part 4.
This is the "aha" that ties the whole talk together: part 1's observability isn't just for debugging; it's the substrate on which evaluators that look at the process (not just the result) run. Useful when how the answer was reached matters (which tools, how many turns).

Our ace in the hole: calibration

def _compute_ece(results, n_bins=10):
    # gap between declared confidence and real accuracy, per bin
    ...
    ece += (len(bucket) / n) * abs(bin_acc - bin_conf)

We already compute ECE (Expected Calibration Error) + a reliability diagram in evals/metrics.py. In other words: when the model says 0.9 confidence, is it right 90% of the time?

Lots of people measure accuracy; few measure calibration. It's a strong differentiator to show in the talk.
Highlight what we already do well. Calibration is sophisticated and uncommon. If confidence is miscalibrated, we can't use confidence thresholds to escalate to a human. It's a great example of a custom eval that goes beyond accuracy.

Online evaluation: evaluate prod ✅ delivered

from pydantic_evals.online import OnlineEvalConfig, OnlineEvaluator
from pydantic_evals.online_capability import OnlineEvaluation

# 3 cheap checks (no LLM): OutputNotEmpty, ConfidenceInRange, LanguageMatches
def build_online_capability(s: Settings) -> OnlineEvaluation | None:
    if not s.online_eval_enabled:        # OFF by default
        return None
    wrapped = [OnlineEvaluator(evaluator=ev,
                               sample_rate=s.online_eval_sample_rate,   # 0.05
                               max_concurrency=s.online_eval_max_concurrency)
               for ev in (OutputNotEmpty(), ConfidenceInRange(), LanguageMatches())]
    return OnlineEvaluation(wrapped, config=OnlineEvalConfig(default_sample_rate=..., enabled=True))

# Agent(model, capabilities=[capability])  → injected via get_llm_service()

Dispatched async after the run → zero added latency in the response; sample_rate + max_concurrency bound the footprint. Emits OTel gen_ai.evaluation.result events. Verified live: /triage untouched.

Delivered and off by default (opt-in via env). Imports: OnlineEvaluation lives in online_capability; OnlineEvalConfig/OnlineEvaluator in the public pydantic_evals.online. max_concurrency is per-evaluator (OnlineEvaluator), not in the global config. I verified pydantic-ai 1.104 supports Agent(capabilities=...) — that was the main risk of this phase. The capability dispatches async after the run, so it doesn't touch /triage latency.

The most useful lesson

The regression gate failed on the first real run (~0.92): two status cases were stably predicted as shipments.
  • It wasn't the harness or a model bug: they were borderline labels in the wrong suite (Anthropic, step 7: read the transcripts).
  • We didn't lower the threshold to fake it → we re-curated them into capability + 2 clear replacements.
  • Bonus: we found a run with many errors was passing vacuously → error-rate guard ≤ 20%.

Final regression: accuracy 1.000 · macro-F1 1.000 · errors 4% → PASS

This is the talk's moral, grounded in practice: evals aren't just numbers, they're a diagnostic tool. The "failure" taught us something about the dataset and made us harden the gate. That's exactly the virtuous cycle Anthropic preaches.

Takeaways

  • One signal, many uses: OTEL spans serve debugging, dashboards and evals.
  • Prompt versioning: save ≠ promote; the app consumes by label; code fallback; rollback with no redeploy.
  • Evals: deterministic graders first, LLM with calibration (and an “Unknown” exit), and read the transcripts.
  • Consistency: for support, pass^k > single-run accuracy.
  • A gate you loosen so it passes is not a gate — re-curate the dataset, not the threshold.
