El output es un contrato Pydantic

Parte 1

Observabilidad OTEL
con Logfire

Arrancamos por lo conocido para asentar el lenguaje OTEL, que después reusamos en evals.

¿Qué es OpenTelemetry?

Un estándar abierto (CNCF), vendor-neutral, para generar telemetría: traces, metrics y logs.

Separa instrumentar de almacenar

Instrumentás una vez con la API/SDK; exportás a cualquier backend (Logfire, Jaeger, Grafana, Datadog…).

Semantic conventions

Nombres estándar de atributos (http.method, gen_ai.*) → herramientas distintas entienden lo mismo.

tu código → OTEL SDK → [Collector opcional] → backend (Logfire)

La idea fuerza: no quedás casado a un vendor. Si cambiás de backend, la instrumentación sigue igual.

Punto de partida conceptual. OTEL es a la observabilidad lo que SQL a las bases: un estándar. Lo importante para el equipo: instrumentamos contra OTEL, no contra Logfire. Logfire es intercambiable. Las semantic conventions son clave: gen_ai.* es la convención para LLMs, y por eso los eventos de online-eval (gen_ai.evaluation.result) son estándar.

Anatomía de un span

El span es el ladrillo. Un span = una unidad de trabajo con nombre y duración.

  • name + start/end (→ duración) + status (ok/error).
  • attributes: pares clave–valor (baja cardinalidad).
  • trace_id = todo el request · span_id = este paso · parent → árbol.
  • context propagation: el trace_id viaja entre funciones/servicios → traza distribuida.
with logfire.span("triage.sync") as span:
    span.set_attribute("endpoint", "sync")
    span.set_attribute("email.body_chars", n)
    result = await llm.triage(req)   # span hijo
    span.set_attribute(
        "triage.result.category", cat)

El handler abre un span; el run del LLM y la llamada httpx cuelgan como hijos → un árbol que cuenta la historia del request.

Acá aterrizamos el vocabulario que usamos toda la charla. El span tree es literalmente lo que vemos en Logfire y lo que después leen los span-based evaluators (ctx.span_tree). trace_id/span_id también van en cada log de structlog para correlacionar logs ↔ traces.

¿Qué es Logfire?

El backend de observabilidad de Pydantic — OTEL-native, no propietario.

SDK ergonómico sobre OTEL

logfire.span(), metric_*() y auto-instrumentación de una línea. Por debajo es OTEL puro.

Pydantic-aware

Entiende Pydantic AI, validaciones y modelos — instrumentación rica sin esfuerzo.

Consultable con SQL

Las traces se consultan con SQL (Postgres detrás): dashboards y alertas sobre tus atributos.

Producción

Scrubbing (PII), sampling (head/tail) y, lo nuevo: prompt management + evals.

Como es OTEL, mañana podés mandar la misma señal a otro backend sin tocar el código.

Logfire = SDK fino + backend. El diferencial vs otros: nace de Pydantic, así que entiende Pydantic AI nativamente, y todo es consultable con SQL. Pero lo más importante para no generar lock-in: por debajo es OTEL estándar. Y las dos features que usamos en las partes 3 y 4 (prompt management y evals) viven acá mismo.

Tres señales, un protocolo

Traces / spans

El árbol de lo que pasó en un request: handler → LLM → httpx.

Metrics

Contadores e histogramas agregados: latencia, errores, confidence.

Logs

Eventos estructurados con request_id (structlog en JSON).

Logfire es un backend OpenTelemetry: instrumentás una vez y la misma señal sirve para debug, dashboards y evals.

La idea clave: OTEL es un estándar abierto. Logfire es solo el backend. Y lo más importante para hoy: la misma señal de spans que usamos para observar producción es la que después leen los span-based evaluators.

Parte 2

Fundamentos de evals

Basado en “Demystifying evals for AI agents” — Anthropic, 2026.

Cambiamos a teoría de evals. Es el marco conceptual que después implementamos con Pydantic Evals.

¿Qué es un eval?

Un test para un sistema de IA: input → lógica de grading → medida de éxito.

La analogía útil (Pydantic): Case + Evaluator = un unit test · Dataset = la suite · Experiment = correr pytest y obtener un report.

La diferencia con unit tests: los sistemas de IA son probabilísticos. El score suele ser cualitativo/gradual, no pass/fail binario.

Definición simple. La analogía con testing baja la ansiedad del equipo: ya saben escribir tests. La diferencia es el no-determinismo, que obliga a pensar en scores graduales y en correr múltiples veces.

Tres familias de graders

Code-based

match exacto, regex, static analysis, state checks.

✅ rápido, barato, reproducible
❌ frágil ante variantes válidas

Model-based (LLM judge)

rúbricas, comparación pairwise.

✅ flexible, capta matices
❌ no determinista, necesita calibración

Human

SME review, A/B, inter-annotator.

✅ gold standard
❌ caro y lento

Regla de Anthropic: deterministas siempre que puedas, LLM donde haga falta, humanos para calibrar.

El proyecto ya tiene los dos primeros: code-based (igualdad de categoría + métricas) y model-based (el JudgeAgent). Lo que falta es la capa humana, aunque sea spot-check, para calibrar el judge. La regla de oro: no uses LLM judge si un check determinista alcanza.

Capability vs Regression

capability

“¿Qué sabe hacer bien?”
Arranca con pass rate bajo. Es la colina para subir. Mide progreso.

regression

“¿Sigue haciendo lo que hacía?”
Pass rate ~100%. Protege contra retrocesos. Una caída = algo se rompió.

Implementado: regression 25 casos (5×categoría, gate estricto 0.95) · capability 22 casos (edge/english/tone, trend 0.70). make eval-regression con --check sale ≠0 si baja del umbral.
Hallazgo real: status-003/004 se predecían estable como shipments (ambigüedad defendible). En vez de bajar el umbral, los recuramos → a capability, y agregamos 2 casos de status claros a regression. Un gate que aflojás para que pase no es un gate.
Distinción clave de Anthropic, ya implementada. El dataset.jsonl mezclado se partió en dos suites disjuntas. El hallazgo de los status ambiguos es el ejemplo perfecto del paso 7 de Anthropic (leer transcripts): el harness no estaba roto ni el modelo — eran etiquetas borderline en la suite equivocada. Se movieron a capability y regression quedó en 100%.

No-determinismo: pass@k vs pass^k

pass@k

Probabilidad de al menos 1 éxito en k intentos.
Sube con k. “Con que aciertes una vez, alcanza.”

pass^k

Probabilidad de que los k pasen.
Baja con k. Para agentes customer-facing.

75% por trial, 3 trials → pass^3 = 0.75³ ≈ 42%. Nuestro temperature=0.2 no es 0: el mismo email puede clasificar distinto. Para soporte, pass^k es la métrica honesta.
Implementado: --repeat K (vía repeat= del framework) + compute_pass_hat_k() desde case_groups(), con lista de flaky (correctos en algunos-pero-no-todos los runs). make eval-passk K=5.
Ya implementado. Como respondemos a clientes reales, importa "acierta siempre", no "alguna vez". pass^k cuenta solo los casos correctos en los k runs; un run que erroró cuenta en contra. Invariante testeado: pass^k ≤ accuracy. También endurecimos el gate: si >20% de los casos erroran (rate limit), la accuracy se calcula solo sobre sobrevivientes y podía pasar vacuamente — ahora el gate lo detecta y falla.

Roadmap de Anthropic, en 8 pasos

  1. Empezá temprano — 20–50 tasks de fallas reales alcanzan.
  2. Partí de lo que ya testeás a mano (bugs, soporte).
  3. Tasks no ambiguos + reference solution.
  4. Sets balanceados (testeá cuándo SÍ y cuándo NO).
  5. Harness robusto + entorno aislado por trial.
  6. Graders pensados; partial credit; LLM judge con salida “Unknown”.
  7. Leé los transcripts — no confíes en el número solo.
  8. Cuidado con saturación; mantené la suite viva.

Un eval al 100% ya no da señal de mejora — solo sirve de regresión.

No hace falta cientos de casos para empezar. El paso 6 — leer transcripts — es el más ignorado y el más importante: un score que no sube puede ser un grader roto, no un modelo malo. Lo conectamos después con la vista de Logfire.

Parte 3

Prompt versioning
con Logfire

Sacar el prompt del código sin redeploy.

Primer pedido central. Hoy el prompt está hardcodeado; vamos a versionarlo.

El problema

SYSTEM_PROMPT = """You are an email triage system..."""   # en services/llm.py
  • Cada ajuste de prompt = commit + redeploy.
  • No hay historial de “qué prompt estaba en prod el martes”.
  • Rollback = revertir código y volver a deployar.
  • Producto/soporte no pueden tocar el prompt sin tocar el repo.
Plantear el dolor antes de la solución. El prompt es el parámetro que más iteramos en un agente, y es justo el que está más acoplado al deploy.

Dos conceptos: prompt y version

Prompt

La unidad que autorás. Tiene name (Email Triage System), slug (email-triage-system), template y settings.

Version

Snapshot inmutable del template (v1, v2, v3…) con autor y timestamp. Congela solo el texto, no los settings.

Y un tercero: el label (ej. production) — un puntero movible hacia una versión. La app consume por label, no por número.
El modelo mental es como git tags + un puntero "production". Las versiones son inmutables; el label production se mueve. Importante: la versión congela solo el texto del template.

Save ≠ Promote

1
Save

Guardás una versión en la página Prompts. Iterás drafts libremente.

2
Promote

Movés el label production en Managed Variables. Recién acá cambia lo que prod importa.

Separar ambos pasos = iterar sin riesgo + promoción explícita y auditable.

Este desacople es la clave de gobernanza: guardar muchas versiones no afecta producción hasta que movés el label conscientemente. Y el rollback es solo mover el label de vuelta.

El código en la app (lo que quedó)

import logfire
from functools import lru_cache

# ⚠️ logfire.var() REGISTRA la variable y NO es idempotente → a nivel módulo, una vez.
_VAR = logfire.var(name='prompt__email_triage_system', default=SYSTEM_PROMPT)

@lru_cache(maxsize=1)                 # resuelto 1×/proceso, NUNCA por request
def get_system_prompt() -> str:
    return _VAR.get(label=settings.prompt_label).value
    # si Logfire no responde → ResolvedVariable.reason == 'code_default'
    # → usa el default en código: el critical path no se rompe.

# Gobernanza prompt ↔ Category (guard en el lifespan, avisa, no crashea)
def assert_category_coverage(prompt: str) -> None:
    missing = [c.value for c in Category if c.value not in prompt]
    if missing:
        _log.warning("prompt.category_drift", missing_categories=missing)

Dos sorpresas de producción: logfire.var() se registra una sola vez (si la llamás 2× explota), y .get() devuelve un ResolvedVariable con .value — no es context manager.

El patrón REAL que terminó en el repo. Descubrí en vivo que logfire.var() no es idempotente: llamarla dentro de una función rompía el test-suite con "already registered". Por eso vive a nivel módulo y solo .get() se llama por resolución, cacheado con lru_cache (resuelto una vez en el lifespan, cero fetch por request). El default garantiza el fallback. Y el guard de categorías protege la gobernanza: si alguien edita el prompt en la UI y borra una categoría, avisa por log sin tumbar el servicio.

Aplicado a email-triage ✅ entregado

  1. ✅ get_system_prompt() resuelve por label, inyectado vía Depends() (patrón DI del repo).
  2. ✅ Resuelto una vez en el lifespan (@lru_cache), no fetch por request — el critical path (1–3 s) no paga lookup.
  3. ✅ default=SYSTEM_PROMPT: la fuente de verdad sigue en código; Logfire solo la sobreescribe si hay versión publicada.
  4. ✅ Guard de gobernanza prompt ↔ Category (avisa si la UI borra una categoría).
Paso manual (UI): crear el prompt y mover el label production es de la persona. El código funciona con el fallback hasta que eso exista. Rollback en vivo: mover el label a v(n-1) — sin commit, sin deploy.
Entregado respetando los patrones del repo (DI, lifespan). La fuente de verdad de las categorías sigue siendo el código (default + enum Category + guard); Logfire da agilidad para iterar el texto. Crear/promover en la UI es el único paso manual, y el código no depende de él para arrancar.

Code-first: todo se define en Python (o YAML/JSON serializado). Si tenés Logfire, los resultados aparecen en la web UI para comparar y colaborar.

Filosofía code-first: a diferencia de plataformas 100% web, acá los evals viven en el repo, versionados con git, y Logfire es la capa de visualización. Esto encaja con cómo ya trabajamos.

Un eval mínimo, end-to-end

from pydantic_evals import Case, Dataset
from pydantic_evals.evaluators import Evaluator, EvaluatorContext, IsInstance

case = Case(
    name='refund_es_01',
    inputs={'subject': '¿Puedo devolver mi pedido?', 'body': '...'},
    expected_output='refunds',
    metadata={'difficulty': 'easy', 'lang': 'es'},
)

class CategoryMatch(Evaluator[dict, str]):          # tu is_correct, como evaluator
    def evaluate(self, ctx: EvaluatorContext[dict, str]) -> float:
        return 1.0 if ctx.output == ctx.expected_output else 0.0

dataset = Dataset(
    name='email-triage',
    cases=[case],
    evaluators=[IsInstance(type_name='str'), CategoryMatch()],
)

async def task(inputs: dict) -> str:
    resp = await llm.triage(TriageRequest(**inputs))
    return resp.category.value

report = dataset.evaluate_sync(task)                # = correr la suite
report.print(include_input=True, include_output=True)

Detalle real del repo: expected_output está tipado como el output del task (TriageResponse), así que la categoría esperada la guardamos en metadata (CaseMeta) y el evaluator la lee de ahí.

Acá se ve cuánto de lo que ya teníamos calza directo: cada línea del jsonl es un Case, is_correct es un Evaluator, run() es evaluate_sync. La migración fue mecánica. El único ajuste no obvio: como expected_output debe ser del tipo del output, la categoría ground-truth vive en metadata, no en expected_output. Reusamos metrics.py sin tocarlo, reconstruyendo EvalResult desde report.cases.

LLM judge: casero vs built-in

Hoy: evals/judge.py
JudgeAgent con rúbrica de 5 dimensiones (relevance, language_match, tone, correctness, overall), temperature=0.1.

from pydantic_evals.evaluators import LLMJudge

dataset.add_evaluator(LLMJudge(
  rubric=(
    "El reply es educado, en el mismo "
    "idioma y no inventa datos del pedido."
  ),
))
Implementado: el JudgeAgent se reusa dentro de un Evaluator custom (JudgeQuality); sumamos verdict="unknown" para que abstenerse en vez de inventar (excluido de las medias + unknown_rate), y --judge-sample N exporta a evals/calibration/*.jsonl para spot-check humano.
No tiramos el JudgeAgent: lo envolvimos en un Evaluator del framework (scores numéricos → report scores; language_match → assertion; verdict → label). El consejo de Anthropic de la salida "Unknown" lo implementamos como un Literal verdict: cuando abstiene, los scores quedan en None y se excluyen de las medias, pero se cuenta en unknown_rate. El export deja el seam para calibración humana (human_verdict en null para que lo llene la persona).

Nuestro as bajo la manga: calibración

Ya calculamos ECE (Expected Calibration Error) + reliability diagram en evals/metrics.py. Es decir: ¿cuando el modelo dice 0.9 de confianza, acierta el 90%?

Online evaluation: evaluar prod ✅ entregado

from pydantic_evals.online import OnlineEvalConfig, OnlineEvaluator
from pydantic_evals.online_capability import OnlineEvaluation

# 3 checks baratos (sin LLM): OutputNotEmpty, ConfidenceInRange, LanguageMatches
def build_online_capability(s: Settings) -> OnlineEvaluation | None:
    if not s.online_eval_enabled:        # OFF por defecto
        return None
    wrapped = [OnlineEvaluator(evaluator=ev,
                               sample_rate=s.online_eval_sample_rate,   # 0.05
                               max_concurrency=s.online_eval_max_concurrency)
               for ev in (OutputNotEmpty(), ConfidenceInRange(), LanguageMatches())]
    return OnlineEvaluation(wrapped, config=OnlineEvalConfig(default_sample_rate=..., enabled=True))

# Agent(model, capabilities=[capability])  → se inyecta vía get_llm_service()

Despacho async tras el run → cero latencia en la respuesta; sample_rate + max_concurrency acotan el footprint. Emite eventos OTel gen_ai.evaluation.result. Verificado en vivo: /triage intacto.

Entregado y apagado por defecto (opt-in por env). Imports: OnlineEvaluation vive en online_capability; OnlineEvalConfig/OnlineEvaluator en el público pydantic_evals.online. El max_concurrency va por-evaluator (OnlineEvaluator), no en el config global. Verifiqué que pydantic-ai 1.104 soporta Agent(capabilities=...) — era el riesgo principal de esta fase. La capability despacha async después del run, así que no toca la latencia de /triage.

La lección más útil

El gate de regresión falló en la primera corrida real (~0.92): dos casos de status se predecían estable como shipments.
  • No era el harness ni un bug del modelo: eran etiquetas borderline en la suite equivocada (Anthropic, paso 7: leé los transcripts).
  • No bajamos el umbral para maquillar → los recuramos a capability + 2 reemplazos claros.
  • Bonus: descubrimos que un run con muchos errores pasaba vacuamente → guard de error-rate ≤ 20%.

Regresión final: accuracy 1.000 · macro-F1 1.000 · errors 4% → PASS

Esta es la moraleja de la charla aterrizada en la práctica: los evals no son solo números, son una herramienta de diagnóstico. El "fallo" nos enseñó algo del dataset y nos hizo endurecer el gate. Eso es exactamente el ciclo virtuoso que predica Anthropic.

Para recordar

  • Una señal, muchos usos: los spans de OTEL sirven para debug, dashboards y evals.
  • Prompt versioning: save ≠ promote; la app consume por label; fallback en código; rollback sin redeploy.
  • Evals: graders deterministas primero, LLM con calibración (y salida “Unknown”), y leé los transcripts.
  • Consistencia: para soporte, pass^k > accuracy de una corrida.
